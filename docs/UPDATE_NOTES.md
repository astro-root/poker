# 総合アップデート 作業メモ（2026-10-23）

このメモは、今回の変更の根拠・未確認事項・デプロイ手順をまとめたものです。**実行・確認できたこと**と**できていないこと**を分けて書いています。

## 1. AIがオールインすると全員フォールドする問題

**結論：ゲームエンジンの不具合ではなく、AIの判断入力の誤り（多人数扱い）が主因でした。**

- 確認したこと：`betting.ts` / `hand.ts` のオールイン適用、サイドポット、アクション順、ラウンド終了判定は、テストで正しく動作（`test/ai-allin.test.ts`）。例外時に暗黙でフォールドする経路は見つかりませんでした（`practice.ts` の例外処理は通知を出すだけ）。
- 原因：`ai.ts` の判断が、**まだ行動していないプレイヤー（降りるかもしれない相手）まで「倒すべき相手」として数え**、勝率の算出と強さの割引に使っていました。4人卓で1人がオールインすると、実際に倒す相手は1人なのに3人分で評価され、過度に弱気になります。
- 修正：`committedOpponentCount`（ベットに合わせた/オールイン中の相手の数）を追加し、**コールを迫られている場面の評価にだけ**使用。AIが必ずコールするようには変更していません。
- 実測（強制プリフロップ・フルスタック・オールイン、乱数による手札、4人卓）：

| レベル | 修正前：降りた割合 / 全員が降りた割合 | 修正後 |
| --- | --- | --- |
| 中くらい（400回） | 66% / 34% | 58% / 27% |
| 強い（25回） | 87% / 60% | 73% / 28% |

- 残る高めのフォールド率は、**100BBのオールインを受けるコール価格が約50%の勝率に相当する**ため、相手の手が不明なら手札の約半分を降りるのが数学的に妥当です。「強い」の標本数（25回）は小さく、統計的な結論としては弱い点に注意してください。AIの強さ設計を変えたい場合は、運営者の判断が必要です。

## 3. 性能調査（通信遅延）

**測定はできていません**（この環境にSupabaseの実環境・ブラウザ・ネットワークがないため）。したがって「高速化した」とは主張しません。コードから確認できた事実と変更点：

- 既存：stateポーリングは `sinceRevision` で未変更時に小さい応答を返し、在席の書き込みは5秒に1回に抑えられていた。
- 変更：①ポーリングの**重複実行を防止**（応答待ち中は次を送らない）。②間隔を状況別に調整（対戦中のハンド進行中 1.2秒、待機・終了画面 3秒、非表示タブ 10秒。従来は一律1.5秒）。待機・終了画面の通信量は減る一方、**対戦中の反映は従来(1.5秒)より最大0.3秒速くなる程度**で、劇的な改善ではありません。
- **Realtime は未導入**。理由：公開チャンネル名がそのまま招待権限になる設計の検討、Edge Function からの配信呼び出し追加、実環境での検証が必要で、検証なしに入れるのは危険と判断。導入するなら「Broadcast で更新通知だけ送り、状態は従来どおりEdge Function経由で取得」が安全です。
- 楽観的更新は行っていません（サーバー応答後に反映）。

## 4. セキュリティ確認結果

**コードとテストで確認したこと**
- 認証：全アクションで JWT の `sub/role/exp` を検査。`config.toml` は `verify_jwt = true`（テストで固定）。
- 権限：ホスト/プレイヤー/観戦者をサーバーで判定。クライアントが送る player id は使わず、JWTの `sub` のみを信頼。
- 秘密情報：他人の手札・山札はレスポンスに含まれない（観戦者を含めテスト）。ショーダウンで公開される手札のみ例外。
- DB：`poker_rooms` と `poker_room_rate_limits` は RLS 有効＋`anon/authenticated` の権限を剥奪。サービスロールはEdge Functionの環境変数のみ（クライアントバンドルに含まれないことは `VITE_` 変数が2つだけである点から確認）。
- 競合：revision による楽観ロック（CAS）。設定更新×開始、リマッチ同時押しをテスト。
- XSS：表示名は `textContent` で描画（`node()` ヘルパー）。サーバーで制御文字・双方向制御文字を拒否。

**確認できていないこと（運営者の確認が必要）**
1. **本番の `verify_jwt` が有効か**（Supabaseダッシュボード/`supabase functions list` で確認）。Edge Function は署名を検証せず `verify_jwt` に依存しています。
2. 匿名サインインの濫用対策（Supabase Auth のレート制限/CAPTCHA 設定）。レート制限は**ゲストID単位**のため、新しいゲストIDを大量に作られると回避できます。
3. `npm audit`（依存脆弱性）。ネットワークがなく**未実行**。Node/Vite/supabase-js のバージョン更新要否も未確認。
4. state のメモリ内レート制限は Edge Function の**インスタンスごと**であり、全体では保証されません。
5. `poker_room_rate_limits` の古い行の削除処理は**未実装**（行が増え続けます）。定期削除の導入を推奨。
6. 匿名ユーザーレコード、各サービスログの保持期間。
7. CORS は `*`（Bearer トークン認証のため即座に危険ではないが、将来は `https://poker.astro-root.com` への限定を検討）。

## 6. デプロイ手順

必要な環境変数（秘密値はここに記載しません）：
- Vercel：`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`（公開可能キー）
- Supabase Edge Function：`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`（Supabaseが自動注入。**クライアントやGitに置かない**）

手順：
1. `supabase/migrations/20261023000100_rate_limit_buckets.sql` を適用（`supabase db push`、またはSQL Editorで `supabase/SQL_EDITOR_SETUP.sql` を新規環境に使用）。**既存環境では、関数のシグネチャが変わるため、Edge Function より先に適用**してください。
2. `npx supabase functions deploy rooms`（`verify_jwt = true` のまま）。
3. Vercel に反映（Git push で自動、または `vercel --prod`）。
4. 確認：2つの別ブラウザでルーム作成→設定変更→開始→観戦者でアクセスして手札が見えないこと／ネットワークのレスポンスに他人の手札・`deck` が含まれないこと。

> 旧スキーマと新Edge Functionの組み合わせ（またはその逆）では、`consume_room_rate_limit` の引数不一致で作成・参加・操作が失敗します。順序を守ってください。
